# DECISIONS.md

## Вариант

Номер варианта: 3
Часть А: `weeklyOvertime` возвращает недоработку до нормы `max(0, 40 − sum)`
вместо переработки `max(0, sum − 40)`.
Часть Б: `addRestHours(int[]) → int` — часы отдыха за неделю: `5 × 8 − total`,
но не меньше 0.

## Решение 1

Формулировка: пороги вынесены в константы `DAILY_NORMAL_HOURS = 8`,
`WEEKLY_NORMAL_HOURS = 40`, `MIN_HOURS = 0`, `MAX_HOURS = 16`.
Альтернатива: хардкод чисел в каждом методе.
Обоснование: при изменении требования (например, норма 36) правим одну
строку — `weeklyOvertime`, `addRestHours` и тесты подхватывают новое
значение без правки логики.

## Решение 2

Формулировка: `average`, `weeklyOvertime` и `addRestHours` вызывают
`total(hours)`, а не считают сумму сами.
Альтернатива: локальный цикл суммирования в каждом методе.
Обоснование: DRY — формула суммы в одном месте, ошибка исправляется один раз.

## Ответы на вопросы методички

### Вопрос 1
Наиболее вероятная ошибка — неверное количество значений или не-число
(пользователь путает разделитель, ставит лишний `;`, печатает букву).
Защищает проверка `parts.length != 5` и regex `^(0|[1-9][0-9]*)$` в методе
`parseHours` класса `TimesheetAnalyzer`. Это единственная точка валидации
ввода, до остальных методов «плохая» строка не доходит.

### Вопрос 2
Ключевое правило варианта 3 — формула недоработки `max(0, 40 − sum)` —
содержится в `TimesheetAnalyzer.weeklyOvertime` и продублирована по смыслу
в `addRestHours`. Метод чистый (без состояния, без I/O), переиспользует
`total`, легко тестируется, а порог 40 вынесен в константу
`WEEKLY_NORMAL_HOURS`.

### Вопрос 3
Блок `n4` (бывший TODO A1) на Activity-диаграмме соответствует циклу
`for` в `parseHours`: для каждого элемента проверяется regex
`^(0|[1-9][0-9]*)$` и диапазон [0, 16], затем делается `Integer.parseInt`.
Блок `n3` — это проверка `parts.length != DAYS_IN_WEEK`, а `n8` —
бросок `IllegalArgumentException`.

### Вопрос 4
Изменение порога дневной переработки (например, 8 → 9) затронет один
метод `overtimeDays` и одну константу `DAILY_NORMAL_HOURS`. Благодаря
централизации константы не нужно править другие методы — их логика
не зависит от конкретного числа. Аналогично изменение нормы 40 → 36
затронет только `WEEKLY_NORMAL_HOURS` (и оба метода недоработки).

## Фрагмент кода для анализа

Ошибка: `i <= hours.length` — off-by-one, при `i == 5` произойдёт
`ArrayIndexOutOfBoundsException`, хотя массив валиден (5 элементов, индексы
0..4). Причина — неверное граничное условие цикла. Исправление:
`for (int i = 0; i < hours.length; i++)`. Это прямо нарушает R1: корректная
строка из 5 значений должна обрабатываться без падения.
